Today I moved the production Docker image build off my laptop and into GitHub Actions. Until now, I built the image locally and pushed it to the registry before deploying with Kamal. It worked, but it meant every deploy depended on my machine's architecture, my cache, and my memory of which tags I had pushed last.

{{image: github-actions-build | The image build job in GitHub Actions, finishing in a little over four minutes}}

What changed

  • The workflow now builds the image on every push to main that touches the app
  • The image is tagged with the commit SHA, so every deploy maps back to exact code
  • Kamal reads the image from the registry instead of building it on the deploy step

Things that went wrong

The first run failed because the build ran out of memory while compiling native gems. Limiting gem install and native compile parallelism in the Dockerfile fixed it. The second problem was a label mismatch: the Kamal service label was missing from the Actions build, so the image was harder to find in the registry. Adding the label to the build step solved it.

I also forgot that the build cache in Actions is separate from the one on my laptop. The first build took about nine minutes. After the cache warmed up, the same build dropped to just over four.

What I'm keeping an eye on

  • Registry storage costs, since every commit now leaves an image behind
  • Whether the job stays fast enough that nobody is tempted to skip it
  • That the deploy workflow never runs against an image that is still building

Notes for next time

Keep the Dockerfile's dependency layers stable so the cache stays useful. If the build slows down again, check whether a dependency change invalidated a layer earlier than expected.
